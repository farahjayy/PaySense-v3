# PaySense v2 — Changelog

> Mandatory session log. Add an entry after **every** session where code changed, a decision was made, or a plan was modified. Newest first. Even a one-line fix gets a one-line entry.

Entry format:
```
### YYYY-MM-DD — [short summary of session goal]
- **Changed:** what files/components were touched and why
- **Decided:** any architectural or design decisions and the reasoning
- **Deviations:** anything that differed from the plan, and why
- **Verified:** what was actually run, and the result (not "should work")
- **Known issues / next steps:** what was left open
```

Those five lines are the floor, not the ceiling. Add these when the session earns them — a debugging session in particular is unreadable without the first two:
- **Reported:** the symptom in the user's own words, before you knew the cause
- **Diagnosed:** what you found, and how you proved it — the reproduction, not the hypothesis
- **Trade-off:** what this change costs, and who it costs it to
- **Noted, not changed:** something you found and deliberately left alone, so the next session doesn't re-investigate it

Rules that make this file worth keeping:
- **"Verified" means a command was run.** Name it and give the result. If nothing was run, write "nothing verified this session" — that is useful information.
- **Deviations are the most valuable line.** A plan that changed silently is a plan nobody will trust next time.
- **Write what you learned, not what you touched.** "Fixed the player" ages into nothing. "The provider's iframe navigates the top context, which sandbox flags block" is still worth reading in six months.
- Don't rewrite history. Corrections go in a new entry that references the old one.

### 2026-10-09 — P3 Engine 1 evaluation built, audited and run; the global LSTM wins (D-34)
- **Changed:** `backend/ml/engine1_eval/` (data type and loaders for the synthetic cohort, MoneyData and Berka; metrics; rolling-origin harness; naive / moving-average / AutoARIMA / Prophet / global-LSTM candidates; HLN Diebold-Mariano, Wilcoxon, Friedman-Nemenyi, Holm; runner; report), `data/external/{moneydata,berka}/download.py` and README, `reports/engine1/` (generated), ADR D-34, ASSUMED 9 and 10.
- **Datasets (all obtained without a login, resolving ASSUMED 3):** the synthetic cohort (60 test profiles at three history lengths; 3,000 training profiles for the LSTM), MoneyData (one real UK account, checksum verified against Mendeley) and 60 of Berka's 4,500 accounts (CTU public guest database; two re-downloads gave identical SHA-256). The author's private log was not used.
- **Decided:** **D-34** serve the global LSTM via ONNX. The rule (D-06) was applied mechanically by `report.py`; the geometric-mean MASE aggregate (ASSUMED 10) and the removal of a contradictory tie rule were fixed after a small smoke run and before the full run, and recorded as such in the execution doc.
- **Reported (by the audits, before the full run):** the margin-versus-MASE conflict (weekly MASE rewards the median), one flat-history Berka series dominating an arithmetic mean, partial-window leakage risks in the LSTM cutoff, unpaired averaging when a model fails, refits for the margin metric, an inert DM test, an unbounded Berka loader and a download that could leave a short file. All fixed or recorded in the execution doc.
- **Result:** LSTM 0.815 (geometric-mean MASE at 13 weeks) against 1.044 for the 13-week moving average and 1.046 for AutoARIMA; median per-series difference -0.110 (95% CI -0.150 to -0.078); best on every dataset and at 17, 26 and 52 weeks of history; first on 13-week cumulative-margin error overall (AutoARIMA is better on the synthetic cohort, 2.13 against 2.90); about 1 ms per forecast against 250-600 ms for Prophet and AutoARIMA. Per-series Diebold-Mariano agrees on Berka (73% of accounts significantly better) but is conservative on the synthetic cohort (8%), because 13 origins per series overlap heavily; the paired Wilcoxon over 242 series is the decision test, as pre-registered.
- **Unflattering:** the LSTM under-forecasts spend (mean signed error about -0.27 naive-error units on synthetic spend, -0.94 on Berka spend); intervals are below nominal on real data (coverage about 0.6-0.75 against 0.8); no synthetic series has interval coverage at all (too few origins); MoneyData's spend includes fixed bills and probably own-account transfers; the LSTM was never fine-tuned on real data.
- **Verified:** `cd backend && uv run ruff check . && uv run pytest -q` → **1315 passed** (this includes the 95 engine1 tests and the later P4/P5 tests), 20 integration deselected; `uv run python -m ml.engine1_eval.run --config full` → 45,804 result rows, 0 failures (about 90 minutes); `uv run python -m ml.engine1_eval.report --config full` run twice → empty diff; the small config ran end to end on real data twice. **Not verified:** the evaluation on any machine other than this one; torch determinism across machines.
- **Noted, not changed:** the margin criterion stays a co-check (ASSUMED 9: the author may want it co-primary, which would amend D-06); Berka pre-training of the LSTM (D-25) was not done; the full run's raw results (`data/engine1/full/`) are gitignored and reproducible from the config.

### 2026-10-08 — Design change: no balance (D-27), limit-capped financing (D-28); P1 built
- **Reported (author, in her words):** if the user doesn't enter a complete, balanced history the forecast is wrong; "usually tracking apps do not have current balance"; a RM600 purchase over 3 months is fine on RM2,000 monthly income but not on RM2,000 savings or on RM500 income; and a provider limit changes the calculation — "limit 200, want to buy 300, then I pay RM100 at checkout and the rest can use SPayLater", with or without interest.
- **Decided:** **D-27** — Engine 1 forecasts income and expense flows; no starting balance, no running ledger, no balance sync. Monthly margin = income − bills − instalments (incl. checkout payments) − discretionary; cumulative margin starts at RM0; shortfall = cumulative margin < RM0 at a month-end; that is Engine 2's label. Engine 2's balance features are replaced by margin- and income-based ones (`margin_monthly_p50_without`, `margin_cum_p10_without`, `income_p10_monthly`); `income_to_due_gap_days` is dropped (the label no longer sees intra-month timing). P3 must also evaluate the forecasters on a weekly unconfirmed-income series. **D-28** — `financed = min(price, remaining limit)`, the excess is a checkout payment in the purchase month; the cap applies to the financed total payable including fee (`ASSUMED`); features `upfront_to_income`, `limit_utilisation_with_purchase`, `limit_known`. **D-29** — API money is integer sen; refunds/transfers are reserved categories; CSV import is stateless with duplicate flagging. Her three RM600 cases are now designed tests for P4.

### 2026-10-08 — P0/P1 reviews applied (security, FastAPI/Python, React/TypeScript)
- **Reviews:** three independent review agents read the code (the first attempts were killed by an API session limit and re-run). **No CRITICAL findings.** The money maths and the limit split were verified (the reviewer brute-forced ~5,000 price/limit/rate/count combinations against an exhaustive search: 0 mismatches). User scoping held on every path traced.
- **Diagnosed and fixed (HIGH):**
  - *Ambiguous writes.* A client timeout after Postgres committed looks like a failed write, so "on error, delete the payment I logged" could erase the payment of an instalment that really was paid, unrepairably. Fixed structurally (**D-30**): a payment is tied to its instalment by a unique key, logging is idempotent, `mark_paid` re-reads on error and never deletes a payment, `create_plan` flips checkout instalments only after their payments are logged and cleans up each step independently. The test fake gained an "apply then fail" injection so this case is actually tested.
  - *Request bodies were read in full before authentication, with no cap* (a 60 MB unauthenticated upload was written to disk before the 401). New body-size middleware: declared-length check plus a streaming count, 2 MiB default, 6 MiB for the CSV upload, 413 envelope with CORS headers.
  - *Ordinary input produced 500s:* blank/NUL text, explicit `null` on PATCH, absurd dates, a >128 KB CSV field, database rejections. Now clean 422/409 via trimmed text types, null-rejecting patch models, a 2000–2100 date window and an `APIError` handler that never echoes database messages.
- **Fixed (MEDIUM/LOW):** server "today" is Malaysia time (UTC was a day behind for 8 hours); schedule dates no longer drift after a short month (bought on the 31st: 28 Feb, 31 Mar, 30 Apr…); `Debit Amount`/`Credit Amount` CSV headers no longer lose credits; `DuitNow`/`Digital`/`Business` no longer match `duit`/`digi`/`bus`, and unsigned-file income guesses are flagged for review; CSV parsing stops at the row limit, caps column count and date-cell length, and skips amounts above the API limit; onboarding never moves backwards and a failed onboarding write no longer fails a saved import; `delete_many` batches ids (the 500-row rollback would have exceeded URL limits); summary/fingerprint reads select only the columns they need and the summary query moved into a repository; a limit too small to split reports `limit_exhausted`; 409/413 responses are documented in the OpenAPI; conflict responses typed for the client.
- **Frontend (React review, no CRITICAL/HIGH):** login now works when sessionStorage is blocked (held in memory) and no longer bounces silently on an unknown persona value; the username field stays focused while signing in; hint/error text is linked with `aria-describedby`; `ink-muted` darkened to `#6e6c64` (4.7:1) and login-panel text raised to `white/90` to meet WCAG AA (ratios computed, not estimated); the login form is first on phones (`min-h-dvh`); a production build now fails without `NEXT_PUBLIC_API_BASE_URL`; a late 401 for an old token cannot wipe a newer session; cached query data is dropped when the session ends; basic security headers added; e2e uses its own build directory so it cannot collide with `npm run dev`. New tests drive a real 401 through the real client, middleware and AuthGate, and cover hydration.
- **Deviation:** `bnpl_installment_id` + `unique (id, user_id)` on instalments added to the (still unapplied) migration; `tzdata` added as a dependency (Windows has no system time-zone database); the fake now also enforces an `in()` size limit, column projection and JSON-serialisable payloads.
- **Deferred, on purpose (recorded in STATUS Known gaps):** per-user write quotas and a cap on ledger size; pagination on `GET /transactions` and SQL aggregation for the month summary and used-limit (both load whole ledgers today); the concurrent-create limit race; refund clipping across months; a full script-src/connect-src CSP (needs nonces; P8); axe accessibility tests, a skip link and per-page titles (P7); escaping `= + - @` in any future spreadsheet export (P9); `uvicorn --limit-concurrency` and proxy limits (P8). Moving create/pay into Postgres functions (`supabase.rpc`) for true transactions was considered and rejected for now (D-30).
- **Verified:** backend `uv run ruff check . && uv run pytest -q` → **909 passed**, 20 integration deselected (written, skipped); frontend lint, `tsc`, **85 Vitest tests**, `gen:api`/`check:api`, `next build` (and the build fails without the API-URL variable, as intended), Playwright 6 passed on desktop + Pixel 7 — all against the in-memory fake. **Still nothing run against Supabase.**
