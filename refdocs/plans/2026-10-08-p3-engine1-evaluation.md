# Plan — P3 Engine 1 evaluation

> Phase P3 of `refdocs/paysense-v2-PRD.md` §6. Execution doc: `refdocs/execution/2026-10-08-p3-engine1-evaluation.md`.
> A plan says **what and why**. The execution doc says **how and in what order**.

## Why this exists

Engine 1 (financial health forecasting) forecasts the two variable weekly series that the product cannot know in advance: **discretionary spend** and **income that is not a confirmed recurring item**. Everything else is a known flow placed on its date (D-27). v1's single net-cash-flow series lost to trivial baselines (v1-lessons), so the question this phase answers, with evidence a supervisor can audit, is: **which forecaster should the product serve, and does it actually beat the benchmarks?**

The decision rule is already fixed (D-06): rolling-origin evaluation, pooled MASE as the primary metric; the served model is the best *literature* candidate (ARIMA / Prophet / LSTM) unless it is significantly worse than the best benchmark, in which case the benchmark is served and that is reported as a finding. Nothing in this phase may change the rule after seeing results.

## What changes because of D-27 (read before building)

- Two series are evaluated, not one: weekly discretionary spend, and weekly income. The PRD's "unconfirmed income" series depends on recurring detection, which is built in P4 (ASSUMED 10). P3 therefore evaluates **total weekly income** for the synthetic cohort (what `weekly_series.csv` carries) and, where a dataset allows, the fixed/variable split by its own ground truth (Berka payment-type codes). Which part of income is "confirmed" is a P4 decision that does not change which model forecasts the remainder best; P3 records this limitation.
- There is no balance series anywhere. The metric that mirrors the product is **cumulative-margin error** over a horizon (income minus spend, accumulated), not a balance error.

## Scope

**In:**
- **Datasets.** (1) The synthetic cohort (`data/synthetic/weekly_series.csv`, 10,000 profiles, discretionary spend and income). (2) MoneyData (real UK account, CC BY 4.0), aggregated to weekly spend and income. (3) A Berka subsample (real multi-account bank data, research use) for the multi-series benchmark and fixed/variable ground truth, **if obtainable without a paid account** (ASSUMED 3, D-25). (4) Optional: the author's own private log, run locally only, never committed. A download script per external dataset under `data/external/`, raw files gitignored.
- **Candidates (fixed by D-05):** Naive (last value), seasonal-naive where meaningful, moving average, AutoARIMA (statsforecast), Prophet, and a **global LSTM** (one model across series). Only benchmarks and configurations may be added; nothing else without an ADR.
- **Harness.** Expanding-window rolling-origin evaluation with a fixed minimum training length and horizon, identical across candidates; one prediction-interval method for every candidate (the residual bootstrap used in serving) so intervals are comparable.
- **Metrics.** MASE (primary, pooled across series), RMSSE, interval coverage and width, and cumulative-margin MAE over the 4- and 13-week horizons.
- **Significance.** Per-series MASE compared with the Harvey–Leybourne–Newbold-corrected Diebold–Mariano test, Wilcoxon signed-rank, and Friedman with Nemenyi post-hoc across all models. Multiple-comparison handling stated.
- **Outputs.** `reports/engine1/` tables, figures and a README generated by script, benchmarks in every comparison, results reported even when unflattering. The winner chosen by the D-06 rule and recorded as an ADR.
- **Sensitivity.** The result on the synthetic cohort is reported next to the result on the real datasets; if they disagree, that is the finding.

**Out (and why):**
- Serving, recurring detection, Monte Carlo of monthly margin, the API (P4).
- Any model outside D-05 (ETS, foundation models are future work, recorded in the research note).
- Tuning on the test windows. Hyperparameters are chosen on earlier origins only.

## Approach

1. Data first: loaders for each dataset that all return the same tidy weekly frame (`series_id, week_start, value, kind`), with the real-data loaders tested on tiny fixtures that mimic the format (no real data committed).
2. The harness and metrics with unit tests on hand-computed examples (MASE, RMSSE, coverage, DM/HLN).
3. Benchmarks first, then ARIMA, Prophet, LSTM, each behind the same `Forecaster` interface (`fit(history) -> forecast(horizon, quantiles)`), so the harness never special-cases a model.
4. A small run end to end (a few hundred series) to catch problems cheaply, then the full run, with every random choice seeded and the run configuration recorded in the output.
5. Report generation last, from stored results; the ADR is written from the generated table, not from memory.

## Risks & unknowns

| Risk / unknown | Confidence | Mitigation |
|---|---|---|
| Berka cannot be downloaded without login or payment | Medium | Documented fallback (PRD Q3): MoneyData + synthetic cohort only; the global LSTM trains on the cohort. Ask the author only if the download needs her account |
| **Circularity:** the synthetic cohort is generated by the author's own process | High | Real datasets are reported separately and given equal weight in the decision narrative; the AR(1)/payday structure in the generator is listed in the report as the thing a model could exploit |
| Short series: students have 4+ months (≈17+ weeks) of history, which is little for ARIMA/Prophet/LSTM | High | Evaluate at the product's real minimum history lengths (17, 26, 52 weeks), not only on long series; report the dependence on history length |
| Prophet and statsforecast are slow at 10,000 series × many origins | Medium | Subsample series for the full comparison (documented sampling, fixed seed), run the cheap models on everything; record wall-clock per model, because serving latency matters in P4 |
| The global LSTM wins on the cohort only because it learns the generator | Medium | Train it on a split of *profiles* disjoint from the test profiles; also evaluate it zero-shot on MoneyData/Berka |
| Torch is not allowed in the served process (D-15) | Known | Training and evaluation use torch offline; if the LSTM wins, export to ONNX in P4 and re-check its accuracy after export |
| Statistical tests over many series declare trivial differences significant | Medium | Report effect sizes (median MASE difference with a bootstrap CI) beside p-values |

## Definition of done

- `cd backend && uv run pytest tests/ml` passes, including hand-computed metric tests, a leakage test (no candidate sees data after the forecast origin; a deliberately leaky "oracle" forecaster scores near zero MASE, proving the harness would notice), and a determinism test (same seed ⇒ identical results table).
- `uv run python -m ml.engine1_eval.run --config small` completes on a small sample and `--config full` completes on the full sample; both write `reports/engine1/` (tables, figures, README) from stored results, and a second run produces an empty `git diff`.
- Every comparison table contains the naive and moving-average benchmarks; the README states which datasets were available, which were not, and why.
- The winner is chosen by the D-06 rule (stated before the run in the execution doc, applied mechanically by the report script) and recorded as ADR D-32 with the table that justifies it; PRD §7 gets the one-liner.
- The `ml-auditor` agent has reviewed the harness for leakage and the report for honesty; findings fixed or listed in STATUS.
