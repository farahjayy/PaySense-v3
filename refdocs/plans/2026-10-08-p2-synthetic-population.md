# Plan — P2 Synthetic population

> Phase P2 of `refdocs/paysense-v2-PRD.md` §6. Execution doc: `refdocs/execution/2026-10-08-p2-synthetic-population.md`.
> A plan says **what and why**. The execution doc says **how and in what order**.

## Why this exists

The supervisor's biggest methodology concern (academic-constraints §2) is the synthetic data: *why* synthetic, *how* each variable is sampled, how dependencies are kept, how the label is assigned, and how representative it is. There is no public dataset of Malaysian students' transactions with BNPL plans, so v2 generates one — **once**, from **one cited parameter file** (D-08), and uses it three ways: Engine 2's ~10,000 training profiles, Engine 1's synthetic cohort, and the three UAT persona CSVs. P2 builds that generator and the evidence that it is defensible. It builds no model and assigns no label (the label is Engine 1's simulation, P5).

## What changes because of D-27 / D-28 / D-29 (read before building)

- **No balance is generated** (D-27). A profile is a flow process: income, bills, discretionary spend, existing BNPL plans, and a proposed purchase. Nothing in the generator needs an opening balance.
- **Income is a modelled series, not a constant.** Engine 1 now forecasts unconfirmed income as well as discretionary spend (PRD §3.1), so the generator must produce the three income shapes the personas stand for: a fixed monthly allowance (budget-conscious), allowance plus lump-sum PTPTN disbursements (most students), and irregular gig/part-time income (irregular-income).
- **Existing and proposed BNPL plans are built with the app's own code** (`domain.schedule`, `domain.plan_builder`): the same sen maths, the same provider rules, and the **limit split** (D-28). A plan the generator makes is a plan the app could have made.
- **Transactions use the app's schema and its categorisation vocabulary** (reserved `Refund` / `Transfer` / `BNPL` categories, `domain.flows.classify`), so the persona CSVs import through P1's importer and mean the same thing to Engine 1.

## Scope

**In:**
- `backend/ml/datagen/params.yaml` + a validating loader: every parameter carries a value, a unit and **either** a `source` key (resolved in `sources.md` to a real reference and, where it exists, a figure) **or** `assumed: true` with a rationale. The loader refuses a parameter with neither, and prints the assumed list.
- Deterministic generation under a master seed (`SeedSequence.spawn`, one child per profile) — the same seed gives the same dataset whatever the profile count or order.
- A transaction-level generator: income process, fixed bills, discretionary spend (weekly totals with over-dispersion, day-of-week profile, payday and exam-week effects, occasional outliers; split into merchant-style transactions with descriptions the categoriser recognises), BNPL plans and their instalment payments, refunds and transfers (so the reserved categories are exercised).
- A proposed-purchase sampler (price relative to income, provider, instalment count, fee, limit split) for Engine 2.
- Three persona CSVs (4 months each, bank-export style, committed under `data/personas/`) that import cleanly through `parse_csv`.
- Writers: Engine 2 profile set (JSON lines, gitignored output), Engine 1 cohort (weekly series for discretionary spend and unconfirmed income, gitignored output), and a small committed manifest (seed, parameter hash, counts).
- A **distribution report** (`reports/datagen/`) comparing the generated moments with the cited targets, generated by script, with a README and an explicit limitations section.

**Out (and why):**
- Any label, forecast, model or feature (P4/P5) — P2 only produces inputs.
- Real data of any kind (D-14). Berka / MoneyData downloads are P3.
- A claim that the synthetic population *is* Malaysian students: it is a documented, parameterised stand-in, and the report says which parameters are cited and which are assumed.

## Approach

1. Parameters and provenance first, because the generator is only as defensible as its sources: gather the cited figures (PTPTN rates, Tok & Cheah spend bands, DOSM household expenditure shares, BNM / CCOB repayment statistics, provider rules from `bnpl-billing-rules-my.md`), write each into `params.yaml` with its citation, and mark everything else `assumed`.
2. Build the generator bottom-up with a test per component (income, bills, discretionary, BNPL events), each checking a distribution property under a fixed seed.
3. Assemble profiles; check determinism and schema validity (every generated transaction passes the same validation the repository applies).
4. Persona CSVs next, imported through the real importer — the earliest end-to-end check that P1 and P2 fit.
5. The cohort and profile writers, then the distribution report last, because it reads the finished generator.

## Risks & unknowns

| Risk / unknown | Confidence | Mitigation |
|---|---|---|
| Some cited figures (DOSM HES category shares, PTPTN disbursement split) cannot be retrieved exactly | Medium | Record the figure only if it was read from the source; otherwise the parameter is `assumed` and appears in the limitations list — never a number that looks cited but isn't |
| **Circularity:** Engine 1 may look good on a cohort generated by a process similar to its own assumptions (weekly over-dispersed spend) | High | Make the generator richer than the forecaster (day-of-week, payday and exam effects, outliers, regime shifts); report cohort results separately from real-data benchmarks (Berka/MoneyData, P3); state it in the limitations |
| Persona realism: a CSV that looks wrong to a tester undermines UAT | Medium | Calibrate each persona to its documented target ranges; author reviews the three CSVs before P9 |
| Determinism breaks when profile order or count changes | Medium | One child `SeedSequence` per profile index; a test generates 10 and 100 profiles and asserts the first 10 are identical |
| Large outputs bloat the repo | Low | Only the three persona CSVs and a manifest are committed; the cohort and profile set are regenerated by script and gitignored |
| The generator needs `numpy`/`pandas`/`pyyaml`, which the API does not | Low | Add them to a dev/`ml` dependency group; `app/` must not import `ml/` |

## Definition of done

- `cd backend && uv run pytest tests/ml` passes: provenance rule (no parameter without a source or `assumed`), determinism (same seed ⇒ identical profiles; a 10-profile run is a prefix of a 100-profile run), schema validity of every generated transaction, plan validity (every generated plan passes `plans_repo`'s validation), and component distribution properties.
- `uv run python -m ml.datagen.personas` regenerates the three CSVs byte-for-byte; a test imports each through `parse_csv` and asserts months of history ≥ 4, no skipped rows, and income / spend within the persona's documented range.
- `uv run python -m ml.datagen.report` writes `reports/datagen/` (tables + figures + README) from a fresh generation, listing every `assumed` parameter.
- Ruff clean; `app/` does not import `ml/` (a test greps for it); no file under `data/personas/` or `reports/datagen/` contains anything that looks like real personal data.
