# Plan — P7 Frontend

> Phase P7 of `refdocs/paysense-v2-PRD.md` §6. Execution doc: `refdocs/execution/2026-10-09-p7-frontend.md`.
> A plan says **what and why**. The execution doc says **how and in what order**.

## Why this exists

Everything so far is invisible to a student. P7 turns the API into screens a tester can use without help: bring a bank statement in, see whether the next three months hold up, ask "is this BNPL purchase safe?", and keep the plans they take. The frontend has **no logic of its own about money**: it renders what the API computed (CLAUDE.md "Surfaces": it cannot talk to Supabase, compute any score or forecast, or hold provider rules). Its job is clarity, honesty about uncertainty, and every state a real person will hit.

## What the earlier phases require of the screens

- **Honest uncertainty.** Engine 1's bands are narrower than nominal on short histories and the model was trained on synthetic students (`reports/engine1/serving_check.md`, `reports/engine2/README.md`). Numbers are shown as estimates, bands as ranges, and the warnings the API returns (stale ledger, suspect months, unmatched confirmed items, `fallback` bootstrap, capped horizon) sit **next to the number they qualify**, not in a footer.
- **The locked state is a first-class screen.** Under four months of history the forecast is locked (`needs_four_months` or `no_usable_history`); the screen says what is missing and offers the import, with a progress indicator, not an error.
- **Money.** Every amount arrives as integer sen and is shown as RM with two decimals through one formatter (`lib/money.ts`); inputs are parsed by the same code, never by `parseFloat` (D-29).
- **Terminology.** User-facing text says "financial health forecast" and "BNPL risk check"; "Engine 1" and "Engine 2" never appear (PRD glossary). No dates or deadlines in copy beyond the user's own data.
- **The author-committed behaviour checks** (academic-constraints §5) are verified through the UI by the end-to-end journey.

## Scope

**In:**
- A typed data layer over the generated client (TanStack Query), one shared error/loading/empty/locked treatment, and a small component kit: stat tile, band badge, score ring, banner, empty state, skeleton, table, dialog, tabs, money input, date input, segmented control.
- Charts (Recharts): the cumulative-margin fan (P10 / P50 / P90 with the zero line and the worst month marked), monthly margin bars, the with-and-without comparison on the risk screen. Each chart has a text equivalent (a table) for screen readers and for the evaluation chapter's screenshots.
- Screens: **Onboarding / import** (CSV upload, column preview, per-row edit and skip reasons, duplicate flags, confirm), **Dashboard** (health score, margin fan, monthly margins, data-quality warnings, bills due soon, locked/stale states), **Transactions** (list with filters, add / edit / delete, month summary), **Recurring** (detected suggestions with one-tap confirm that sends the match text, manual add / edit / pause), **Plans** (list, create with the live limit-split preview, detail with mark-paid and bulk pay, bills by month, provider limits), **Risk checker** (form → result with probability, band, plain-language reasons, the smallest change that reaches Safe, with-and-without chart, repayment flag, data-quality notes → confirm → plan and frozen report), **Risk report** (the frozen view), **Model card** (what the model is, what it was trained on, its limits, versions).
- Every screen has loading, empty, error and locked states, designed (not default), at 375, 768 and 1440 px.
- Accessibility to WCAG 2.2 AA as far as automation and keyboard testing can show: landmarks, a skip link, page titles per route, focus management on dialogs and route changes, colour never the only signal (bands carry text and an icon), contrast tokens already in `globals.css`, reduced-motion respected, axe checks in tests.
- A Playwright journey on desktop and a phone profile: log in → import a persona CSV → dashboard → risk check → confirm → plan visible.

**Out (and why):**
- Any client-side computation of scores, forecasts or provider rules.
- Accounts, sign-up, passwords (supervisor decision), push notifications, native apps (PRD §5).
- Production deployment (P8) and the UAT kit (P9).

## Approach

1. Foundations first: formatters and the money input (already tested), the data layer, the component kit with tests, the shell with all routes and page titles.
2. Screens in the order a tester meets them: import → dashboard → transactions / recurring → plans → risk checker → report → model card. A screen starts when its endpoint is green (all are, by P6).
3. Design direction chosen up front and written into `globals.css` tokens and the component kit so screens do not drift: the v1 warm editorial light theme (PRD requirement), with deliberate hierarchy: a large score and one clear sentence first, evidence below, controls last; restrained colour used for meaning only (band colours, the zero line), generous spacing rhythm instead of uniform padding.
4. Test each component and screen with Testing Library against mocked API responses typed by the generated schema; axe on every screen; then Playwright against the real FastAPI app on the in-memory database.
5. Reviews last (react, TypeScript, accessibility).

## Risks & unknowns

| Risk / unknown | Confidence | Mitigation |
|---|---|---|
| The screens drift from the API contract | Medium | Types come only from `schema.d.ts`; `check:api` in CI; mock responses typed by the same schema |
| Chart accessibility and bundle size | Medium | Recharts loaded only on screens that use it (dynamic import); a table alternative for every chart; bundle budget from the web rules (app page JS under 300 kB gzipped) |
| The uncertainty is misread as certainty | High | Estimates labelled as such; ranges, not points; warnings adjacent to the number; the model card states the synthetic training data plainly |
| Import is the first thing every tester does and is easy to get wrong | High | Preview-before-save, skip reasons per row, duplicate flags, a sample file link to the persona CSV format; Playwright covers it |
| Next.js 16 conventions differ from memory | Medium | Read the bundled guides (`node_modules/next/dist/docs/`) before using an API; heed deprecations |
| Mobile layouts cramp tables and charts | Medium | Cards instead of tables below 768 px; chart height and tick density adapt; tested at 375 px |

## Definition of done

- `cd frontend && npm run lint && npx tsc --noEmit && npm run test && npm run build` pass; `npm run check:api` passes; `npx playwright test` passes on desktop and phone profiles.
- Every screen has loading, empty, error and locked states with tests; every chart has a text alternative; axe reports no violations on any screen.
- The end-to-end journey passes, and the designed cases (Safe at RM2,000, At Risk at RM500, at risk with no income) are visible through the UI in a Playwright test.
- Coverage on `frontend/lib` is at least 80%; no component computes money beyond formatting.
- Screenshots at 375 / 768 / 1440 are generated by script for the evaluation chapter.
- `react-reviewer`, `typescript-reviewer` and `a11y-architect` have reviewed; findings fixed or listed in STATUS.
