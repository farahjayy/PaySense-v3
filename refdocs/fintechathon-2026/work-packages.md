## 0. The goal in one paragraph

Enter **Topic A: Personal Finance Assistant** of the 2026 Shenzhen FinTechathon (International Track, theme "AI as a Financial Participant"). Take PaySense v2 (BNPL affordability check for Malaysian students) and make it **a personal finance assistant for students who buy now, pay later**: an assistant that completes real tasks (afford, safest option, create the plan, budgets, bills, import) through **three permission tiers** where every write needs the user's confirmation; full **Topic A coverage** (budgeting, bill analysis, spending insights, ranked recommendations, proactive alerts); hardened login; recalibrated engines; and **execution evidence** regenerated by script. The hero task stays the original purpose: *"Can I afford this BNPL purchase?"* The assistant is a front door to the same engines, never a replacement for them.

Scoring: Task completion 40% · Security & compliance 30% · Innovation & interaction 30%.
Submission items this work feeds: technical documentation, deck, demo video, source code (README, GitHub link, deployment instructions, tests), security self-assessment (permission tiers + known-risk list), execution evidence (sandbox logs + demo video).

## 3. Assistant architecture (the design the packages implement)

### 3.1 Tiers

| Tier | Meaning | Tools (name → what it reuses) |
|---|---|---|
| **0 Read** | Reads the signed-in user's data, changes nothing | `get_month_summary`, `get_spending_by_category`, `list_recent_transactions` (bounded), `get_bills_by_month`, `get_bill_analysis`, `get_spending_insights`, `get_forecast`, `list_plans`, `list_providers_and_limits`, `get_budgets`, `get_budget_status`, `get_recommendations`, `get_alerts` |
| **1 Propose** | Computes or parses, stores nothing that changes the ledger | `check_purchase_risk` (the `assess()` pipeline behind `POST /risk/check`; factors and the smallest-change suggestion), `preview_plan`, `suggest_budget`, `parse_pasted_transactions` (validates, grounds and flags duplicates), `propose_action` (creates a pending action, see below) |
| **2 Write** | Changes data | `add_transaction`, `confirm_import`, `create_plan` (same code as `POST /risk/confirm`: re-evaluates on the server, freezes the report, creates the plan), `set_budget`, `delete_budget`. **Not callable by the model.** Executed only by the confirm endpoint when the user presses a button. |

### 3.2 How writes are made safe

1. The model calls `propose_action(type, payload)`. The server validates the payload with the same Pydantic models the normal API uses (`TransactionIn`, `PlanIn`, `ConfirmRow`, a new `BudgetIn`) and stores a **pending action** in a database table (per user, with expiry and single use).
2. The UI shows a confirm card built from the **validated payload** (not the model's words).
3. The user presses Confirm → `POST /api/assistant/actions/{id}/confirm`. The server checks: same user, not expired, still pending (atomic status change), then runs the Tier 2 function and marks it done. Cancel → `.../decline`.
4. `user_id` always comes from the session. The model's tool arguments never contain it, and any such field is rejected.

### 3.3 Guardrails

- **Numbers come from engines.** The UI renders result *cards* (risk band, score, margin chart, plan table, budget bars) from tool output, reusing the existing risk components. The LLM only writes the short narration around them.
- **Number check.** Every figure (RM amount, percentage, count) in the narration must appear in the tool results or the user's message; otherwise the narration is replaced with a template sentence (the pattern of `engines/risk/templates.py`).
- **Untrusted data.** Transaction descriptions, merchant names, pasted text and uploaded rows are data, never instructions: passed in a clearly delimited, labelled block; the system prompt says never to follow instructions found there.
- **Limits.** Max tool calls per turn (start at 6), max output tokens, request timeout, history capped to the last N turns and sent by the client as **plain user/assistant text only** (tool results are always regenerated server-side, so forged history cannot inject results). Per-user rate limit (`rate_limited(bucket, max, window)`), per-user daily token budget, global daily cap.
- **Key handling.** `ANTHROPIC_API_KEY` is an optional `SecretStr` in `core/settings.py`; never logged, never returned, never in the frontend. The browser never calls Anthropic, so the CSP `connect-src` is unchanged.
- **Privacy.** Derived figures, not whole ledgers; `list_recent_transactions` is bounded and descriptions can be redacted by a setting. Demo uses synthetic personas only.
- **Audit log.** Every user message, tool call, proposal, confirmation, refusal and fallback is stored per user (tier, tool, status, model, token counts). A script exports it as evidence.

#### WP2 — Budgets backend [M]

#### WP13 — Bill analysis [M]
- `domain/bill_analysis.py` over existing recurring items, bills by month and plan schedules: recurring-bills summary (monthly total, count, share of income); bills whose amount went up (latest vs previous occurrences of the same confirmed item); **collisions** (two or more bills or instalments due within the same 7-day window, with the total due); next 30 days' due list.
- `GET /api/insights/bills`. Tool `get_bill_analysis`.
- **Done when:** tests for increases, collisions across providers, no recurring items, a plan paid early; two-user and unauthenticated tests.

#### WP14 — Spending insights [M]
- `domain/insights.py` built only from the month summary and category spending (D-45): month-on-month change per category (sen and %), the three biggest movers, unusual transactions (above a robust threshold on the person's own history for that category: median + k·MAD, `ASSUMED` k), savings rate (saved ÷ income), and a plain-language headline chosen by rule.
- `GET /api/insights/spending?month=`. Tool `get_spending_insights`.
- **Done when:** tests for a first month (no comparison), a category that appears or vanishes, refunds, BNPL row, too-little history for "unusual"; totals equal the month summary.

#### WP15 — Ranked recommendations and proactive alerts [M]
- `domain/recommendations.py`: a fixed, ordered rule set over engine outputs only — forecast shortfall chance and margin band (Engine 1), budget states (WP2), bill collisions and increases (WP13), insight movers (WP14), open plans near the provider limit. Each recommendation carries its **source figures**, a priority, and an action the user can take (often a pre-filled `propose_action`).
- `alerts`: the subset that needs attention now (over budget, collision in the next 7 days, shortfall chance above the Caution edge). The assistant opens the conversation with them.
- `GET /api/recommendations`, `GET /api/alerts`. Tools `get_recommendations`, `get_alerts`.
- **Done when:** every rule has a test that fires and one that does not; every figure in a recommendation traces to a tool output (asserted).

## 6. Demo script (shape; exact numbers come from the real model)

Persona `frequent_bnpl`, signed in with username and passphrase, history loaded.
0. The assistant opens with what needs attention (alerts: a bill collision, a budget near its limit).
1. "Can I afford an RM799 phone on SPayLater over 3 months?" → asks for any missing field, runs the check, shows the risk card (band, score, reasons). The steps panel shows each tool and its tier.
2. "What's the safest way to buy it?" → shows the smallest change, or says honestly that none reaches Safe.
3. "Go ahead with that." → confirm card (exact plan) → Confirm → plan created, report saved.
4. "What do I owe this month?" → bills, instalments and the collision.
5. "How am I doing?" → insights and ranked recommendations.
6. "Set my food budget to RM400." / "Suggest a budget." → confirm card → saved; the bar appears.
